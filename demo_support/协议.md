# 用量导出流

HTTP 返回 gzip 文件本身，不设置 Content-Encoding。解压后的 UTF-8 NDJSON 依次为一条 header、多条 usage、一条 trailer；明细 count 按中间物理记录计，totals 按 meter 汇总非 cancel 行的原始 quantity，尚未做 quantity_factor 换算。report/correct/cancel 对应既有业务动作，reason 在更正和取消时随行提供；usage_id 不含导出号。映射绑定 contract_id、side 和版本。

/usage 包含两个 gzip member，?cut=1 截断校验尾部，?bad=1 含不可解析数量，?total=1 总量不符，?rev=1 为 exp-2 的后续修订（u1 correct、u2 cancel）。导出号相同而内容不同需作为冲突保留。

运行 python demo_support/source.py --port 8787 可启动回环来源；运行 python demo_support/check.py 检查样本和故障开关。来源仅产生输入，不调用业务导入。

## 采集入口

python -m meterbook --database 库文件 collect 来源 --session 会话 --mapping 映射 [--chunk 字节]

来源为回环 HTTP 地址或本地 gzip 文件；采集边下载边解压边核对，不要求整份解压进内存，多 gzip member 拼接流与任意网络切块边界均可。会话在 begin 时固定 mapping 的 contract_id、side、revision 与 quantity_factor；header 声明的 mapping_revision 必须与固定版本一致，明细数量按固定 factor 换算后才进入事件流。

核对从原始记录算起：trailer count 按 header 与 trailer 之间的物理行数（含坏行）核对，totals 按非 cancel 有效行的原始 quantity（未换算）逐 meter 做精确十进制比对。坏行计入原始笔数并保留行号与原文；只要存在坏行即无法核平（unverifiable），不会静默丢弃后凑出平账。报告同时给出 raw（原始合计）、valid（有效明细）、quarantined（隔离）与 posted（实际入账结果）。

会话状态：reconciled（核平并已接收入账）、mismatched（流完整但核对不符或无法核平，不入账）、incomplete（尾部截断、gzip 校验失败、末行缺失或超出限额，不声称本次完整）、duplicate（同导出号同内容重试，不变成新账）、conflicted（同导出号不同内容，拒绝并保留双方摘要）。仅 reconciled 执行 report/correct/cancel 接收；事件 sequence 接在该侧流尾之后，事件 ID 由导出号与行号派生。已结算月份的新事件沿用既有 reconcile 与 adjustment 更正流程，旧账单保持原样。

限额：压缩 32 MiB、解压 128 MiB、单行 1 MiB、共 10 万行、单块 base64 1400000 字节。会话运行时驻留进程内，原始压缩块暂存于 export_chunks 供审计；进程退出后未完成会话需换新会话重采。运行 python demo_support/collect.py 可通过本地来源实际演练尾部截断、坏明细、总量不符、后续修订、幂等重试与同号异文冲突。
